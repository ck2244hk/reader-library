Every GPU-facing Vulkan call — image acquisition, command execution, presentation — returns to the CPU immediately, with no guaranteed ordering between them. The entire render loop exists to impose that ordering explicitly, using semaphores between GPU operations and fences between the GPU and the CPU.

The Five-Step Frame Outline
1Wait for the previous frame to finish (CPU waits on a fence)
2Acquire an image from the swap chain (GPU signals a semaphore when ready)
3Record the command buffer that draws onto the acquired image
4Submit the recorded command buffer (waits on the acquire semaphore, signals a render-finished semaphore and a fence)
5Present the swap chain image to the screen (waits on the render-finished semaphore)
Semaphores vs. Fences
VkSemaphore — GPU ↔ GPU ordering
  • Orders queue operations relative to each other
  • Binary: starts unsignaled, becomes signaled, auto-resets to unsignaled once the waiting operation consumes it
  • Operation A signals S on completion; operation B waits on S before starting
  • vkQueueSubmit returns immediately on the CPU — the wait happens entirely on the GPU
  • Host (CPU) is never involved in resetting it
VkFence — GPU → CPU (host) waiting
  • Lets the host block until GPU work signals completion
  • Used via vkWaitForFences — an explicit, blocking host call
  • Must be reset manually with vkResetFences — the host decides when
  • Created with VK_FENCE_CREATE_SIGNALED_BIT to avoid a first-frame deadlock
  • Used here specifically to wait for the previous frame before recording a new one

void mainLoop() { while (!glfwWindowShouldClose(window)) { glfwPollEvents(); drawFrame(); } vkDeviceWaitIdle(device); // drain async work before cleanup() destroys resources }
Logic Flow

Vulkan's foundational design decision is that GPU-facing calls are asynchronous: vkAcquireNextImageKHR, vkQueueSubmit, and vkQueuePresentKHR all return to the CPU immediately, with no implicit guarantee about when the underlying GPU work actually starts or finishes relative to other submitted work. This chapter is entirely about imposing the necessary ordering by hand, using two complementary primitives. Semaphores order GPU operations relative to each other without involving the CPU at all — operation A signals a semaphore, operation B waits on it, and the GPU itself enforces the sequencing while the CPU keeps running. Fences exist for the one place the CPU itself needs to wait: before reusing or rerecording a command buffer, the host must know the GPU has actually finished executing the previous submission of that buffer.

The drawFrame() function strings these together in the exact order: vkWaitForFences blocks the CPU until inFlightFence — set by the previous frame's vkQueueSubmit — signals, confirming the GPU is done with last frame's command buffer. The fence is then manually reset (fences, unlike semaphores, require explicit host-driven reset) before vkAcquireNextImageKHR requests the next swap chain image, supplying imageAvailableSemaphore to be signaled once that image is actually ready to be rendered into. Only after acquisition does the command buffer get reset and rerecorded for this frame's imageIndex.

VkSubmitInfo connects three things: what to wait on before the submitted work starts (imageAvailableSemaphore, gated specifically at the VK_PIPELINE_STAGE_COLOR_ATTACHMENT_OUTPUT_BIT stage — chosen so that earlier pipeline stages like the vertex shader can start executing immediately, even before the swap chain image is confirmed available, since they don't touch the color attachment yet), what to execute (the single recorded command buffer), and what to signal once finished (renderFinishedSemaphore for GPU-side ordering, and inFlightFence for the CPU-side wait at the top of the next drawFrame() call). VkPresentInfoKHR closes the loop by waiting on renderFinishedSemaphore before asking the presentation engine to display imageIndex.

A subtle problem surfaces because the render pass's automatic layout transition (declared back in the render passes chapter) is, by default, assumed to happen at the very start of the pipeline — but at that exact moment the swap chain image may not have been acquired yet, since vkAcquireNextImageKHR's semaphore hasn't necessarily signaled. The fix is an explicit VkSubpassDependency using VK_SUBPASS_EXTERNAL as srcSubpass (meaning "the implicit work that happens outside this render pass") that delays the transition specifically until the COLOR_ATTACHMENT_OUTPUT stage — the same stage the image-available semaphore is already gating in VkSubmitInfo, so the two waits line up correctly.

Finally, because drawFrame() leaves GPU work in flight on every iteration, simply exiting the glfwWindowShouldClose loop and proceeding straight into cleanup() risks destroying semaphores, fences, or other resources the GPU is still using. vkDeviceWaitIdle is called once, after the loop, specifically to drain all outstanding work before any vkDestroy* call runs.

Step-by-Step — drawFrame()
  1. Create imageAvailableSemaphore, renderFinishedSemaphore, and inFlightFence (fence created with VK_FENCE_CREATE_SIGNALED_BIT)
    WHYThe SIGNALED_BIT flag avoids a first-frame deadlock — without it, the very first vkWaitForFences call would block forever since nothing has ever signaled the fence before.
  2. vkWaitForFences(device, 1, &inFlightFence, VK_TRUE, UINT64_MAX), then vkResetFences(...)
    WHYBlocks the host until the previous frame's GPU work is done, guaranteeing it's safe to reuse the command buffer. Manual reset is required because fences don't auto-reset like semaphores.
  3. vkAcquireNextImageKHR(device, swapChain, UINT64_MAX, imageAvailableSemaphore, VK_NULL_HANDLE, &imageIndex)
    WHYRequests the next presentable swap chain image; imageAvailableSemaphore will signal once it's actually ready to be rendered into.
  4. vkResetCommandBuffer(commandBuffer, 0) then recordCommandBuffer(commandBuffer, imageIndex)
    NOTEThe command buffer is rerecorded fresh every frame, targeting the framebuffer for the just-acquired imageIndex.
  5. Build VkSubmitInfo: wait on imageAvailableSemaphore at COLOR_ATTACHMENT_OUTPUT_BIT, run the command buffer, signal renderFinishedSemaphore; call vkQueueSubmit(graphicsQueue, 1, &submitInfo, inFlightFence)
    WATCH OUTpWaitDstStageMask must correspond element-wise to pWaitSemaphores — get the array order wrong and the wrong stage gets gated.
  6. Build VkPresentInfoKHR: wait on renderFinishedSemaphore, target swapChain + imageIndex; call vkQueuePresentKHR(presentQueue, &presentInfo)
    WHYPresentation must not begin until rendering has actually finished writing to the image — that's exactly what renderFinishedSemaphore guarantees.
  7. After the main loop ends, call vkDeviceWaitIdle(device) before cleanup() runs
    WHYdrawFrame() leaves GPU work in flight; destroying semaphores/fences/command pools while that work is still running is invalid and triggers validation errors.
Quiz — 10 Questions
Q1
conceptual
Why does Vulkan require explicit synchronization objects (semaphores, fences) for something as simple as drawing one frame?
ASynchronization objects are only needed when multiple GPUs are present in the system; on a single-GPU system they could be omitted
BThey are required by the windowing system (GLFW), not by Vulkan itself — Vulkan would otherwise run perfectly synchronously
CCalls like vkAcquireNextImageKHR, vkQueueSubmit, and vkQueuePresentKHR are all asynchronous — they return to the CPU immediately with no guaranteed execution order relative to each other unless that order is imposed explicitly
DThey exist solely to prevent validation layer warnings; release builds without validation layers don't need them functionally
Q2
terminology
What is the fundamental difference between a VkSemaphore and a VkFence in this rendering loop?
ASemaphores can be waited on by the host (CPU); fences can only be waited on by other GPU queue operations
BFences are reusable indefinitely without resetting; semaphores must be manually reset by the host after every use
CThere is no functional difference — fences and semaphores are interchangeable aliases for the same underlying Vulkan object type
DSemaphores order GPU queue operations relative to each other without CPU involvement, and auto-reset once consumed; fences let the host (CPU) block until GPU work completes, and must be manually reset via vkResetFences
Q3
gotcha
Why is inFlightFence created with VK_FENCE_CREATE_SIGNALED_BIT instead of letting it start unsignaled like a fresh fence normally would?
ASIGNALED_BIT is required by the Vulkan spec for all fences passed to vkQueueSubmit — it's not optional
BWithout it, the very first call to vkWaitForFences on frame 0 would block forever, since no previous frame ever existed to signal the fence — pre-signaling lets that first wait return immediately
CSIGNALED_BIT makes the fence behave like a semaphore, auto-resetting after each wait instead of requiring vkResetFences
DIt signals to the swap chain that the first frame should skip the layout transition entirely
Q4
application
What does vkAcquireNextImageKHR's semaphore parameter (imageAvailableSemaphore) actually guarantee?
AIt will be signaled once the requested swap chain image is actually ready to be rendered into — acquiring an image index doesn't mean the image is immediately usable
BIt guarantees the image's previous contents have been cleared to black before the function returns
CIt blocks the CPU until the image is ready, making vkAcquireNextImageKHR itself a synchronous, blocking call
DIt signals immediately and unconditionally the moment vkAcquireNextImageKHR is called, regardless of the image's actual readiness
Q5
gotcha
In VkSubmitInfo, why is pWaitDstStageMask set to VK_PIPELINE_STAGE_COLOR_ATTACHMENT_OUTPUT_BIT rather than a stage at the very start of the pipeline (which would seem more "cautious")?
ACOLOR_ATTACHMENT_OUTPUT_BIT is the only valid value Vulkan accepts in this field — no other stage is legal here
BWaiting at the start of the pipeline would cause the fragment shader to run before the vertex shader, corrupting the render order
CGating only at the color attachment output stage lets earlier stages, like the vertex shader, begin executing immediately — they don't touch the color attachment and don't need to wait for image availability, improving pipeline utilization
DIt has no performance implication; the tutorial chose it arbitrarily and any other stage value would behave identically
Q6
terminology
What role does the inFlightFence argument to vkQueueSubmit play, separate from the semaphores in the same call?
AIt tells the GPU which queue family to submit the work to, replacing the need for a separate queueFamilyIndex parameter
BIt will be signaled once the submitted command buffer finishes executing on the GPU — drawFrame() waits on this exact fence at the start of the next frame before reusing the command buffer
CIt signals the presentation engine that the image is ready to display, performing the same role as renderFinishedSemaphore
DIt is purely optional and has no functional effect when passed to vkQueueSubmit alongside semaphores
Q7
gotcha
Why does the render pass need an explicit VkSubpassDependency with srcSubpass = VK_SUBPASS_EXTERNAL, when the render pass already declares an automatic layout transition via initialLayout/finalLayout?
AVK_SUBPASS_EXTERNAL is required syntax with no functional effect — render passes always need at least one VkSubpassDependency to compile
BWithout it, the fragment shader would run before the vertex shader, since subpass dependencies are what enforce shader stage ordering
CThe dependency is needed to specify which queue family owns the image during the transition — VK_SUBPASS_EXTERNAL designates the graphics queue family explicitly
DBy default, Vulkan assumes the layout transition happens at the very start of the pipeline — but at that point the swap chain image may not have been acquired yet. The explicit dependency, using VK_SUBPASS_EXTERNAL to mean "the implicit work outside this render pass," delays the transition until the COLOR_ATTACHMENT_OUTPUT stage, matching when the image-available semaphore is actually gating execution
Q8
application
In VkPresentInfoKHR, why does pWaitSemaphores point at renderFinishedSemaphore rather than imageAvailableSemaphore?
APresentation must not begin until rendering has actually finished writing to the image; renderFinishedSemaphore is exactly the signal that the submitted command buffer's work is done, which is what vkQueuePresentKHR needs to wait on
BimageAvailableSemaphore can only be waited on once per program run, so a second semaphore is needed purely to work around that one-time-use restriction
CBoth semaphores are interchangeable here; the tutorial could equally have waited on imageAvailableSemaphore with identical results
DpresentInfo always waits on whichever semaphore was passed to vkAcquireNextImageKHR, by Vulkan specification — renderFinishedSemaphore is simply an alias for it
Q9
gotcha
Why does mainLoop() call vkDeviceWaitIdle(device) after the glfwWindowShouldClose loop ends, instead of jumping straight into cleanup()?
AvkDeviceWaitIdle is required to flush the GLFW event queue before the window can be destroyed
BIt resets all fences and semaphores to their initial state so cleanup() doesn't need separate vkDestroySemaphore/vkDestroyFence calls
CEach call to drawFrame() submits asynchronous GPU work that may still be executing when the loop exits; destroying semaphores, fences, or command pools while that work is still in flight is invalid and would trigger validation errors — vkDeviceWaitIdle drains all of it first
DvkDeviceWaitIdle is purely a performance optimization with no correctness implications; omitting it would still produce correct, valid behavior
