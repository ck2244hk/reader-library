All the shader stages, fixed-function structs, the pipeline layout, and the render pass finally come together in a single VkGraphicsPipelineCreateInfo — and are compiled into an immutable pipeline object with one call to vkCreateGraphicsPipelines.

The Four Components of VkGraphicsPipelineCreateInfo
Component 01
Shader stages
The VkPipelineShaderStageCreateInfo array describing the vertex and fragment shader modules with their entry points and specialization constants
Component 02
Fixed-function state
Pointers to all the fixed-function structs: vertex input, input assembly, viewport/scissor, rasterizer, multisampling, depth-stencil, and color blending — plus dynamic state
Component 03
Pipeline layout
The VkPipelineLayout handle describing uniform buffers, push constants, and descriptor sets accessible from shaders during draw operations
Component 04
Render pass
The VkRenderPass handle plus the subpass index — the pipeline is validated against this render pass's attachment formats; compatible render passes may also be used

Logic Flow

The conclusion chapter is the assembly step. Every object created in the preceding chapters — shader modules wrapped in stage descriptors, the half-dozen fixed-function structs, the pipeline layout, and the render pass — is referenced by pointer or handle in a single VkGraphicsPipelineCreateInfo. This structure is effectively a complete specification of everything the GPU needs to know about one rendering configuration: how vertex data arrives, how it flows through the programmable stages, how rasterization and blending work, and what the output framebuffer looks like.

Two fields on VkGraphicsPipelineCreateInfo deserve special attention. The subpass field (set to 0) tells Vulkan which subpass within the render pass this pipeline targets — a pipeline is not just tied to a render pass but to a specific subpass within it. The tutorial notes that the pipeline can be used with other render passes as long as they are "compatible" — meaning the attachment properties match — but it cannot be used in a different subpass index without a distinct pipeline object. The pDepthStencilState field is set to nullptr because depth testing is not yet part of the tutorial; Vulkan accepts a null pointer here as long as the render pass's subpass does not use a depth-stencil attachment.

The two "derivative" fields — basePipelineHandle and basePipelineIndex — expose an optimization for applications that create many similar pipelines. By setting VK_PIPELINE_CREATE_DERIVATIVE_BIT in the flags and pointing to a parent pipeline (either by handle or by batch index), Vulkan can reuse driver-internal compilation work from the parent for the derived pipeline. At this point in the tutorial both fields are inactive. The creation function itself, vkCreateGraphicsPipelines (note the plural), accepts an array of create infos and fills an array of pipeline handles, enabling multiple pipelines to be compiled in one driver call — potentially more efficient than independent calls. The second parameter takes an optional VkPipelineCache; when supplied with a cache that was loaded from a file saved in a previous run, the driver can skip redundant shader compilation entirely, dramatically speeding up cold startup in shipping applications.

Step-by-Step — createGraphicsPipeline()
  1. Zero-initialize VkGraphicsPipelineCreateInfo, set sType
    WHYZero-initialization ensures every optional pointer defaults to nullptr rather than garbage — Vulkan reads all pointer fields and a stale pointer causes undefined behavior or validation errors.
  2. Set stageCount = 2 and pStages = shaderStages
    WHYLinks the compiled vertex and fragment shader modules (with entry-point name "main") into the pipeline.
  3. Assign all seven fixed-function state pointers (pVertexInputState through pDynamicState); set pDepthStencilState = nullptr
    WATCH OUTnullptr is only valid for pDepthStencilState when the subpass uses no depth-stencil attachment. Once a depth buffer is added, a real VkPipelineDepthStencilStateCreateInfo is required.
  4. Set layout = pipelineLayout, renderPass = renderPass, subpass = 0
    WHYThe pipeline must know the render pass attachment format for validation, and the subpass index to know which attachments it writes. The layout declares all resource bindings the shaders will access.
    NOTEThe pipeline may be used with other render passes, but only if they are "compatible" — same attachment count, formats, and sample counts for the referenced subpass.
  5. Set basePipelineHandle = VK_NULL_HANDLE and basePipelineIndex = -1
    WHYPipeline derivatives are inactive here. These fields only take effect when VK_PIPELINE_CREATE_DERIVATIVE_BIT is set in the flags field — without that flag, both values are ignored by the driver.
  6. Call vkCreateGraphicsPipelines(device, VK_NULL_HANDLE, 1, &pipelineInfo, nullptr, &graphicsPipeline)
    NOTEThe second parameter is the pipeline cache — VK_NULL_HANDLE disables caching. A VkPipelineCache loaded from disk would accelerate this call on repeat runs by reusing prior compilation output.
    WATCH OUTShader modules referenced in pStages can be destroyed immediately after this call returns — the pipeline holds its own compiled copy of the shader bytecode.
  7. Add vkDestroyPipeline and vkDestroyPipelineLayout to cleanup() in that order
    WHYThe pipeline holds a reference to the layout internally; destroy the pipeline first, then the layout. Both must be destroyed before vkDestroyDevice.
Quiz — 5 Questions
Q1
gotcha
vkCreateGraphicsPipelines is deliberately named in the plural. What does this reflect about the function's design?
AIt creates both a graphics pipeline and a compute pipeline in a single call, since they share the same pipeline layout
BIt is named in the plural because it also creates the pipeline layout and render pass as a side effect
CIt accepts an array of VkGraphicsPipelineCreateInfo structs and fills an array of VkPipeline handles — multiple pipelines can be compiled in a single driver call, which may be more efficient than independent calls
DIt creates one VkPipeline per shader stage — two shader stages means two pipeline objects are created
Q2
gotcha
The tutorial sets pDepthStencilState = nullptr. Under what condition is this valid, and what would break if a depth attachment were added to the render pass?
Anullptr is always valid for pDepthStencilState — if no depth test is wanted, Vulkan ignores the field entirely regardless of the render pass
Bnullptr is valid only when the subpass uses no depth-stencil attachment. If a depth attachment were added to the render pass's subpass, the pipeline would require a real VkPipelineDepthStencilStateCreateInfo — passing nullptr would be a validation error
Cnullptr is valid as long as the fragment shader does not write to gl_FragDepth; the render pass attachment list is irrelevant
DPassing nullptr for pDepthStencilState causes depth writes to be disabled but depth reads to remain active — it is not a null-disables-all shortcut
Q3
terminology
What is a pipeline derivative, and what must you do to activate basePipelineHandle or basePipelineIndex?
AA pipeline derivative is a sub-pipeline that handles a single draw call's state; it activates automatically when basePipelineHandle is not VK_NULL_HANDLE
BA pipeline derivative copies shader bytecode from the parent pipeline; you activate it by setting stageCount = 0 and pointing pStages to the parent's stages
CA pipeline derivative allows the child pipeline to share a render pass with the parent; it is activated by giving them the same pipelineLayout handle
DA pipeline derivative is a new pipeline that reuses driver compilation work from a parent pipeline with similar state, reducing creation cost; it is activated by setting VK_PIPELINE_CREATE_DERIVATIVE_BIT in the flags field — without this flag, basePipelineHandle and basePipelineIndex are ignored
Q4
application
What does passing a valid VkPipelineCache to vkCreateGraphicsPipelines enable, and how can the benefit extend across program restarts?
AThe cache stores compiled pipeline data so that repeated pipeline creations with the same state reuse the cached compilation result instead of recompiling. The cache can be serialized to disk with vkGetPipelineCacheData and reloaded via VkPipelineCacheCreateInfo.pInitialData on the next run, making even cold startup fast
BThe cache stores all VkPipelineCreateInfo structs so you don't need to re-fill them on the next run; it does not cache GPU compilation, only the CPU struct construction
CThe cache shares compiled pipeline objects between threads, reducing synchronization overhead when multiple threads call vkCreateGraphicsPipelines concurrently
DThe cache is an LRU memory pool for VkPipeline handles; when the pool is full, least-recently-used pipelines are evicted and must be recreated if needed again
Q5
conceptual
The tutorial says this pipeline can be used with render passes other than the one it was created against. What is the condition for this, and what does it NOT require?
AThe pipeline can be used with any render pass as long as the same VkPipelineLayout is used — attachment formats are irrelevant once the pipeline is compiled
BThe pipeline can be used with another render pass only if it was created with VK_PIPELINE_CREATE_ALLOW_DERIVATIVES_BIT, which signals driver flexibility
CThe other render pass must be "compatible" — meaning matching attachment counts, formats, and sample counts for the referenced subpass. It does NOT require the exact same VkRenderPass handle; structural equivalence is sufficient
DThe pipeline cannot be used with any other render pass — the handle is baked in at compile time and the driver generates code specific to that exact render pass object
