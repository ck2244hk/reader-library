Vulkan cannot render to a window without a VkSurfaceKHR — the WSI bridge between the API and the OS window system — and adding a present queue family introduces the first place where two required queues might or might not share a physical index.

Logic Flow

Vulkan is window-system agnostic — it has no built-in concept of a screen or window. To display rendered output, the application must create a VkSurfaceKHR, which is an abstract handle representing the OS window as a render target. This is provided by the VK_KHR_surface instance extension (already included through glfwGetRequiredInstanceExtensions). The tutorial first shows the Win32-specific path — VkWin32SurfaceCreateInfoKHR requiring HWND and HINSTANCE — to illustrate what the abstraction hides, then immediately moves to glfwCreateWindowSurface, which handles all platforms with a single call.

Surface creation timing is a non-obvious constraint. The surface must be created right after the instance and before physical device selection. The reason is vkGetPhysicalDeviceSurfaceSupportKHR, called inside findQueueFamilies during device evaluation — it needs a valid VkSurfaceKHR to check whether a queue family can present to that specific surface. Creating the surface after selecting the device would break this dependency.

The QueueFamilyIndices struct gains a presentFamily field alongside graphicsFamily. These represent two different GPU capabilities: graphicsFamily handles draw commands; presentFamily handles the handoff of finished frames to the OS display system. On most desktop hardware with a discrete GPU, the same queue family supports both — but the Vulkan spec does not guarantee this. The tutorial writes code that treats them as potentially distinct to be correct on all hardware, even though in practice they often share the same index.

When both families share an index, naively creating two VkDeviceQueueCreateInfo structs for the same family index violates the spec. std::set solves this elegantly: inserting graphicsFamily.value() and presentFamily.value() into a set automatically deduplicates them. The loop then produces either one or two VkDeviceQueueCreateInfo structs depending on whether the indices are distinct. This means no if-else branching on equality — the set handles it uniformly.

Cleanup ordering grows more complex. vkDestroyDevice still goes first. Then the debug messenger. Then vkDestroySurfaceKHR — the surface is tied to the instance, so it must be destroyed before vkDestroyInstance. GLFW teardown comes last. The presentQueue handle, like graphicsQueue, is implicitly destroyed with the device and needs no explicit call.

Step-by-Step — Adding the Window Surface
  1. Add VkSurfaceKHR surface as a private class member
    WHYThe surface handle must persist from after instance creation through cleanup; it's needed by both findQueueFamilies and swap chain creation in later chapters.
  2. Implement createSurface() using glfwCreateWindowSurface
    WHYGLFW abstracts the platform-specific VkXxxSurfaceCreateInfoKHR structs. One call works on Windows, Linux, and macOS without any #ifdef branching.
    WATCH OUTDo not use vkCreateWin32SurfaceKHR (or its equivalents) alongside GLFW — it defeats the purpose of using a portability library and won't compile on other platforms.
  3. Call createSurface() from initVulkan() immediately after setupDebugMessenger() and before pickPhysicalDevice()
    WHYfindQueueFamilies calls vkGetPhysicalDeviceSurfaceSupportKHR, which requires a valid surface. If the surface doesn't exist during device selection, present support cannot be queried.
  4. Add presentFamily to QueueFamilyIndices and update isComplete()
    WHYThe device must have both a graphics queue and a present queue. isComplete() now requires both — this change automatically propagates the new requirement to isDeviceSuitable() and the findQueueFamilies loop.
  5. In findQueueFamilies(), query each family with vkGetPhysicalDeviceSurfaceSupportKHR and set indices.presentFamily
    WHYPresent support is not implied by VK_QUEUE_GRAPHICS_BIT — a graphics-capable family may not support presentation to a particular surface on certain hardware and window system combinations.
  6. In createLogicalDevice(), replace the single VkDeviceQueueCreateInfo with a vector built from a std::set of unique family indices
    WHYCreating two VkDeviceQueueCreateInfo structs for the same family index is a spec violation. The set deduplicates automatically — when both families share an index, the loop produces one struct; when distinct, it produces two.
  7. Add VkQueue presentQueue as a class member and retrieve it with vkGetDeviceQueue after device creation
    WHYEven if presentQueue ends up pointing to the same underlying queue as graphicsQueue, the handle is used differently at submission time. Keeping them separate in code makes the intent clear and allows hardware with distinct queues to work correctly.
  8. Add vkDestroySurfaceKHR(instance, surface, nullptr) to cleanup() before vkDestroyInstance
    WHYThe surface is created from the instance and must be destroyed before it. Correct order: vkDestroyDevice → debug messenger → vkDestroySurfaceKHR → vkDestroyInstance → GLFW teardown.
    WATCH OUTvkDestroySurfaceKHR takes the instance as its first argument, not the device — unlike most vkDestroyXXX calls for device-level objects.
