A conceptual and procedural breakdown of why Vulkan exists, what it costs to draw a single triangle, and how the API is structured — including the exact 8-step sequence every Vulkan program follows.

Key Terminology
TermDefinitionWhy it matters here
VkInstanceThe root Vulkan object that initializes the API for your applicationEverything starts here — you can't query hardware or do anything else without it
VkPhysicalDeviceA handle representing an actual GPU detected on the systemYou query this to inspect VRAM size, feature support, and queue families before committing

VkSwapchainKHRA collection of render target images the GPU cycles through for frame displayEnsures you always render into an image not currently being shown — prevents tearing

VkShaderModuleA compiled shader loaded from SPIR-V bytecodeVulkan standardized on SPIR-V to eliminate vendor-specific GLSL dialect inconsistencies
VkCommandBufferA pre-recorded sequence of GPU commands (draw calls, pipeline binds, render pass transitions)GPU work is recorded first then submitted — enables reuse across frames and parallel recording
VkCommandPoolA memory allocator for command buffers, tied to a specific queue familyThe pool's queue family constrains which queues its buffers can submit to

Logic Flow

Vulkan was built from scratch because older graphics APIs like OpenGL were designed for fixed-function hardware and then had programmable features grafted on incrementally. The result was driver code bloated with heuristics — guessing at programmer intent to map modern workloads onto architectures the original API never anticipated. This is why the same game can behave differently across GPU vendors, and why driver updates can meaningfully affect performance without touching the game itself. Vulkan's answer is to strip all guesswork from the driver by making the programmer explicitly declare every intent upfront.

The triangle walkthrough is the page's core argument for why that explicitness is necessary at every layer. To render a single triangle you must negotiate with hardware (Instance → PhysicalDevice → Device), establish the display pipeline (Surface → Swapchain → ImageViews → Framebuffers), declare your rendering contract with the driver (RenderPass → Pipeline), and pre-package your GPU commands (CommandPool → CommandBuffer) — all before the main loop begins. Each object in this chain exists because the driver needs information it would otherwise have to guess. The Framebuffer isn't redundant with the Render Pass; the Render Pass defines what attachment slots exist, while the Framebuffer names which actual images fill them.

The most distinctive design decision is pipeline immutability. In OpenGL you can swap shaders at runtime with a single call. In Vulkan, switching shaders or changing vertex layout requires building an entirely new VkPipeline object. The page frames this as the difference between ahead-of-time and just-in-time compilation — by locking in all state upfront, the driver can fully optimize once and produce consistent runtime performance. The cost is that you must anticipate every shader/state combination your program needs and pre-bake each one.

The API conventions section reinforces the same philosophy at a micro level. The vk/Vk/VK_ prefix system, struct-heavy parameter passing, explicit sType fields, and VkResult return codes all push responsibility to the application layer — the driver never absorbs uncertainty. Validation layers are the designated escape hatch: they restore error checking during development by inserting themselves between the API and the driver, then vanish completely in release builds with zero overhead.

Step-by-Step — Triangle Pipeline
  1. Create a VkInstance
    WHYInitializes the Vulkan API for your application — nothing else can exist without this root object.
    WATCH OUTDeclare all required API extensions here (e.g. WSI extensions) — they cannot be added after instance creation.
  2. Select a VkPhysicalDevice
    WHYQueries available GPUs and picks one based on VRAM size, feature support, and queue family availability.
    WATCH OUTA device may have Vulkan support but lack graphics queue families — always verify queue family support during selection.
  3. Create a VkDevice and VkQueue
    WHYCreates the logical interface to the chosen GPU and retrieves the queue handle used to submit all work.
    WATCH OUTYou must explicitly list every VkPhysicalDeviceFeature you intend to use (e.g. multi-viewport) — unspecified features are off even if the hardware supports them.
  4. Create a window, VkSurfaceKHR, and VkSwapchainKHR
    WHYEstablishes the display target — the swap chain provides the ring of images you'll render into and cycle for presentation.
    WATCH OUTSurface and swap chain are WSI extension objects (KHR suffix) — not core Vulkan. Skip this step only if doing pure offscreen rendering.
    • a. Create OS window (e.g. via GLFW)
    • b. Create VkSurfaceKHR from the native window handle
    • c. Create VkSwapchainKHR bound to that surface
  5. Wrap swap chain images into VkImageViews
    WHYRaw swap chain images cannot be used as render targets directly — VkImageView declares how each image is interpreted (format, aspect, mip range).
    WATCH OUTCreate one VkImageView per swap chain image — you'll need to select the right one at draw time.
  6. Create a Render Pass
    WHYDeclares to the driver what image attachments rendering will use and how their contents should be handled (load/store ops like clear-to-black).
  7. Create VkFramebuffers
    WHYBinds specific VkImageViews to the attachment slots declared in the render pass — one framebuffer per swap chain image.
    WATCH OUTFramebuffers must be created after both the render pass and image views exist, and recreated if the swap chain is recreated.
  8. Set up the VkPipeline (graphics pipeline)
    WHYBakes shader modules, viewport, depth ops, blending state, and the render pass reference into an immutable pipeline object the GPU can fully optimize.
    WATCH OUTChanging shaders or vertex layout requires a completely new VkPipeline — pre-create all combinations you need. There is no default blend state.
  9. Allocate a VkCommandPool and record VkCommandBuffers
    WHYGPU commands (begin render pass, bind pipeline, draw, end render pass) must be pre-recorded into command buffers before they can be submitted.
    WATCH OUTRecord one command buffer per possible swap chain image — re-recording every frame is valid but less efficient.
    • a. Create VkCommandPool (tied to a queue family)
    • b. Allocate one VkCommandBuffer per swap chain image
    • c. Record: begin render pass → bind pipeline → draw 3 vertices → end render pass
  10. Run the main loop
    WHYDrives frame production by acquiring a swap chain image, submitting the right command buffer, and returning the image for presentation.
    WATCH OUTQueue operations are asynchronous — use semaphores to ensure render waits on acquisition and presentation waits on render completion.
    • a. vkAcquireNextImageKHR → get image index
    • b. vkQueueSubmit → execute the matching command buffer
    • c. vkQueuePresentKHR → return image to swap chain for display

Why did Vulkan need to be designed from scratch rather than extending OpenGL?
AOpenGL lacked support for fragment shaders on modern GPUs
BOlder APIs accumulated abstractions designed for fixed-function hardware, forcing drivers to guess at programmer intent — causing vendor inconsistency and poor multi-threading
COpenGL was proprietary and Khronos needed an open cross-platform replacement
DMobile GPUs refused to support the OpenGL instruction set

CThey refer to the same underlying object — VkDevice is just the newer API name
DVkDevice handles memory allocation; VkPhysicalDevice handles command submission

terminology

conceptual
Why does Vulkan require creating an entirely new VkPipeline to switch shaders, instead of swapping them at runtime?
AShader modules are stored in read-only GPU memory after compilation
BLocking in all pipeline state upfront is the equivalent of ahead-of-time compilation — it lets the driver fully optimize once, making runtime performance more predictable
CThis is a known limitation of SPIR-V bytecode that will be addressed in a future Vulkan version
DPipeline objects are immutable because they are cached in a shared driver registry across applications
