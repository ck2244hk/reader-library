Logic Flow

Vulkan was built from scratch because older graphics APIs like OpenGL were designed for fixed-function hardware and then had programmable features grafted on incrementally. The result was driver code bloated with heuristics — guessing at programmer intent to map modern workloads onto architectures the original API never anticipated. This is why the same game can behave differently across GPU vendors, and why driver updates can meaningfully affect performance without touching the game itself. Vulkan's answer is to strip all guesswork from the driver by making the programmer explicitly declare every intent upfront.

The triangle walkthrough is the page's core argument for why that explicitness is necessary at every layer. To render a single triangle you must negotiate with hardware (Instance → PhysicalDevice → Device), establish the display pipeline (Surface → Swapchain → ImageViews → Framebuffers), declare your rendering contract with the driver (RenderPass → Pipeline), and pre-package your GPU commands (CommandPool → CommandBuffer) — all before the main loop begins. Each object exists because the driver needs information it would otherwise have to guess. The Framebuffer isn't redundant with the Render Pass; the Render Pass defines what attachment slots exist, the Framebuffer names which actual images fill them.

The most distinctive design decision is pipeline immutability. In OpenGL you can swap shaders at runtime with a single call. In Vulkan, switching shaders or changing vertex layout requires building an entirely new VkPipeline object. The page frames this as the difference between ahead-of-time and just-in-time compilation — by locking in all state upfront, the driver can fully optimize once and produce consistent runtime performance. The trade-off is pre-creating every shader/state combination your program needs.

The API conventions section reinforces the same philosophy at a micro level. The vk/Vk/VK_ prefix system, struct-heavy parameter passing, explicit sType fields, and VkResult return codes all push responsibility to the application. Validation layers are the designated escape hatch — inserting error checking between the API and driver during development, then vanishing in release with zero overhead.

Step-by-Step — Triangle Pipeline
  1. Create a VkInstance
    WHYInitializes the Vulkan API — nothing else can exist without this root object.
    WATCH OUTDeclare all required API extensions here (e.g. WSI extensions) — cannot be added after instance creation.
  2. Select a VkPhysicalDevice
    WHYQueries available GPUs and picks one based on VRAM, feature support, and queue family availability.
    WATCH OUTA device may have Vulkan support but no graphics queue family — always verify during selection.
  3. Create a VkDevice and VkQueue
    WHYCreates the logical GPU interface and retrieves the queue handle for submitting all work.
    WATCH OUTExplicitly list every VkPhysicalDeviceFeature you need — unspecified features are off even if hardware supports them.
  4. Create window, VkSurfaceKHR, and VkSwapchainKHR
    WHYEstablishes the display target — the swap chain provides the ring of images to render into and cycle for presentation.
    WATCH OUTSurface and swap chain are WSI extension objects (KHR) — skip only for pure offscreen rendering.
    • a. Create OS window (e.g. via GLFW)
    • b. Create VkSurfaceKHR from the native window handle
    • c. Create VkSwapchainKHR bound to that surface
  5. Wrap swap chain images into VkImageViews
    WHYRaw swap chain images can't be used as render targets — VkImageView declares how each is interpreted.
    WATCH OUTCreate one per swap chain image — select the right one at draw time.
  6. Create a Render Pass
    WHYDeclares to the driver what attachments are used and how their contents should be handled (load/store ops).
  7. Create VkFramebuffers
    WHYBinds specific VkImageViews to the render pass attachment slots — one framebuffer per swap chain image.
    WATCH OUTMust be created after both the render pass and image views; recreate when swap chain is recreated.
  8. Set up the VkPipeline
    WHYBakes shaders, viewport, depth ops, blending, and the render pass reference into an immutable GPU-optimized object.
    WATCH OUTChanging shaders or vertex layout requires a completely new VkPipeline. There is no default blend state.
  9. Allocate VkCommandPool and record VkCommandBuffers
    WHYGPU commands must be pre-recorded into buffers before submission — one buffer per swap chain image.
    WATCH OUTRe-recording every frame is valid but less efficient — pre-record for static draw sequences.
    • a. Create VkCommandPool (tied to a queue family)
    • b. Allocate one VkCommandBuffer per swap chain image
    • c. Record: begin render pass → bind pipeline → draw 3 vertices → end render pass
  10. Run the main loop
    WHYDrives frame production — acquire image, submit commands, present result.
    WATCH OUTQueue ops are async — use semaphores so render waits on acquisition and present waits on render.
    • a. vkAcquireNextImageKHR → get image index
    • b. vkQueueSubmit → execute matching command buffer
    • c. vkQueuePresentKHR → return image to swap chain
Quiz — 10 Questions
Q1conceptual
Why did Vulkan need to be designed from scratch rather than extending OpenGL?
AOpenGL lacked support for fragment shaders on modern GPUs
BOlder APIs accumulated abstractions designed for fixed-function hardware, forcing drivers to guess at programmer intent — causing vendor inconsistency and poor multi-threading
COpenGL was proprietary and Khronos needed an open cross-platform replacement
DMobile GPUs refused to support the OpenGL instruction set
The page explicitly argues that existing APIs had abstractions designed for fixed-function hardware that couldn't cleanly expose modern GPU features. Vendor inconsistency and driver guesswork — not ownership or mobile refusal — were the core problems.
Q2terminology
What is the difference between VkPhysicalDevice and VkDevice?
AVkPhysicalDevice is for discrete GPUs; VkDevice is for integrated GPUs
BVkPhysicalDevice represents the actual hardware queried for capabilities; VkDevice is the logical interface you create to use it, declaring which features you need
CThey refer to the same object — VkDevice is just the newer API name
DVkDevice handles memory allocation; VkPhysicalDevice handles command submission
VkPhysicalDevice is the hardware handle (queried for VRAM, queue families, feature support). VkDevice is the logical object you create to use it, declaring which VkPhysicalDeviceFeatures you need. Always two separate objects.
Q3terminology
What does the KHR suffix on VkSurfaceKHR and VkSwapchainKHR indicate?
AThese objects are hardware-accelerated and require a Khronos-certified driver
BThese are part of a Vulkan extension (WSI), not core Vulkan — because the core API is intentionally platform-agnostic
CThese are deprecated types maintained only for Khronos compatibility
DThese require kernel-level privileges and direct hardware access
KHR marks a Khronos ratified extension, not core Vulkan. The page explicitly notes Vulkan is "completely platform agnostic" — which is why window/display interaction lives in the WSI extension layer.
Q4conceptual
Why does Vulkan require creating an entirely new VkPipeline to switch shaders, instead of swapping them at runtime?
AShader modules are stored in read-only GPU memory after compilation
BLocking in all pipeline state upfront is the equivalent of ahead-of-time compilation — it lets the driver fully optimize once, making runtime performance more predictable
CThis is a known SPIR-V limitation that will be addressed in a future Vulkan version
DPipeline objects are immutable because they are cached in a shared driver registry across applications
The page uses the ahead-of-time vs. just-in-time analogy directly. Baking all state into VkPipeline upfront gives the driver full optimization context with no runtime ambiguity — the trade-off is pre-creating all combinations you'll ever need.
Q5logic / relationship
What is the relationship between a Render Pass and a VkFramebuffer?
AThey are interchangeable — a framebuffer is just a render pass with image views attached
BThe render pass declares what attachment slots exist and how to handle them; the framebuffer binds specific VkImageViews to those slots
CThe framebuffer declares the attachment layout; the render pass selects which GPU executes it
DA render pass contains multiple framebuffers and selects between them per draw call
The page states this precisely: "a render pass only describes the type of images" while "a VkFramebuffer actually binds specific images to these slots." They are complementary — neither alone is sufficient.

BVK_KHR_display and VK_KHR_display_swapchain, which allow creating a surface representing the entire screen

The page explicitly mentions VK_KHR_display and VK_KHR_display_swapchain as allowing you to "create a surface that represents the entire screen" and notes this "could be used to implement your own window manager."
Q7gotcha
Validation layers sit between the API and the driver. Why are they completely disabled in production builds?
AThey produce visual artifacts in release builds that weren't present during development
BThey require elevated system privileges not available to released applications
CThey add runtime overhead — parameter validation, memory tracking — that's valuable in development but unnecessary once the code is known correct
DThey are incompatible with swap chains in non-debug driver configurations
The page says layers can be "completely disabled when releasing your application for zero overhead." Runtime checking cost only — A, B, and D are invented distractors not mentioned anywhere in the source.
Q8gotcha
The tutorial says to record a command buffer for each swap chain image rather than recording fresh every frame. Why?
AVulkan prohibits re-recording command buffers that have already been submitted
BRe-recording every frame is valid but less efficient — pre-recording allows the same buffers to be reused, the preferred approach for static draw sequences
CCommand buffers are automatically freed after submission and cannot be reset
DThe GPU can only hold one command buffer in memory at a time
The page explicitly says "the alternative would be to record the command buffer again every frame, which is not as efficient." Re-recording is allowed — it's just not the recommended approach for static sequences.
Q9sequence
What must be created before you can create VkFramebuffers?
AVkCommandPool and VkCommandBuffer
BBoth the Render Pass and the VkImageViews — the framebuffer needs slot definitions from the render pass and actual image handles from the image views
CThe VkPipeline — framebuffers must reference the pipeline's output format
DOnly the VkSwapchainKHR — framebuffers are created directly from swap chain images
Step 6 (Render Pass) and Step 5 (Image Views) must both precede Step 7 (Framebuffers) in the pipeline. The framebuffer needs the render pass for attachment slot definitions and the image views for the actual image handles to bind into those slots.
Q10sequence
Which is the correct order of the three main loop calls per frame?

BvkQueuePresentKHR → vkAcquireNextImageKHR → vkQueueSubmit
