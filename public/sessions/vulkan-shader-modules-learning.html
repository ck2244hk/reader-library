Before Vulkan touches a shader, it must be compiled to SPIR-V bytecode — a vendor-neutral intermediate format that eliminates historical GLSL compiler inconsistencies and gives every driver the same unambiguous input to compile to machine code.

Key Code
shader.vert — vertex shader
#version 450 layout(location = 0) out vec3 fragColor; vec2 positions[3] = vec2[]( vec2(0.0, -0.5), vec2(0.5, 0.5), vec2(-0.5, 0.5) ); vec3 colors[3] = vec3[]( vec3(1.0, 0.0, 0.0), vec3(0.0, 1.0, 0.0), vec3(0.0, 0.0, 1.0) ); void main() { gl_Position = vec4( positions[gl_VertexIndex], 0.0, 1.0); fragColor = colors[gl_VertexIndex]; }
shader.frag — fragment shader
#version 450 layout(location = 0) in vec3 fragColor; layout(location = 0) out vec4 outColor; void main() { outColor = vec4(fragColor, 1.0); }
Compile shaders to SPIR-V (Windows)
glslc.exe shader.vert -o vert.spv glslc.exe shader.frag -o frag.spv
readFile() — load .spv binary
static std::vector<char> readFile(const std::string& filename) { std::ifstream file(filename, std::ios::ate | std::ios::binary); if (!file.is_open()) throw std::runtime_error("failed to open file!"); size_t fileSize = (size_t)file.tellg(); // ate → cursor at end = size std::vector<char> buffer(fileSize); file.seekg(0); file.read(buffer.data(), fileSize); file.close(); return buffer; }
createShaderModule() — wrap SPIR-V in a VkShaderModule
VkShaderModule createShaderModule(const std::vector<char>& code) { VkShaderModuleCreateInfo createInfo{}; createInfo.sType = VK_STRUCTURE_TYPE_SHADER_MODULE_CREATE_INFO; createInfo.codeSize = code.size(); createInfo.pCode = reinterpret_cast<const uint32_t*>(code.data()); // ↑ safe: std::vector guarantees worst-case alignment VkShaderModule shaderModule; if (vkCreateShaderModule(device, &createInfo, nullptr, &shaderModule) != VK_SUCCESS) throw std::runtime_error("failed to create shader module!"); return shaderModule; }
createGraphicsPipeline() — stage info structs and module lifetime
void createGraphicsPipeline() { auto vertCode = readFile("shaders/vert.spv"); auto fragCode = readFile("shaders/frag.spv"); VkShaderModule vertModule = createShaderModule(vertCode); VkShaderModule fragModule = createShaderModule(fragCode); VkPipelineShaderStageCreateInfo vertStage{}; vertStage.sType = VK_STRUCTURE_TYPE_PIPELINE_SHADER_STAGE_CREATE_INFO; vertStage.stage = VK_SHADER_STAGE_VERTEX_BIT; vertStage.module = vertModule; vertStage.pName = "main"; // entry point name VkPipelineShaderStageCreateInfo fragStage{}; fragStage.sType = VK_STRUCTURE_TYPE_PIPELINE_SHADER_STAGE_CREATE_INFO; fragStage.stage = VK_SHADER_STAGE_FRAGMENT_BIT; fragStage.module = fragModule; fragStage.pName = "main"; VkPipelineShaderStageCreateInfo shaderStages[] = {vertStage, fragStage}; // ... fixed-function state structs ... // ... vkCreateGraphicsPipeline(...) ... // Modules no longer needed — pipeline has baked the machine code vkDestroyShaderModule(device, fragModule, nullptr); vkDestroyShaderModule(device, vertModule, nullptr); }
Logic Flow

OpenGL accepted GLSL source strings and compiled them inside the driver at runtime. This seemed convenient but created a persistent problem: every GPU vendor wrote their own compiler, and those compilers interpreted the GLSL specification differently. Shaders that worked on NVIDIA would silently misbehave on AMD, or produce driver-specific error messages with no common ground for debugging. Vulkan breaks this cycle by requiring SPIR-V — a compact, well-specified bytecode format. The programmer pre-compiles GLSL to SPIR-V using an offline tool (glslc from Google), giving every driver an identical, unambiguous input to compile to native GPU instructions.

The triangle tutorial writes the minimum two shaders. The vertex shader runs once per vertex. It has no vertex buffer — instead it hardcodes a positions array and a colors array indexed by the built-in gl_VertexIndex. gl_Position receives a vec4 clip-coordinate position (the two 2D coordinates padded with z=0.0 and w=1.0, where w=1.0 means no perspective division effect). The fragColor variable is declared with layout(location=0) out — this passes the color to the next stage. The fragment shader receives it with layout(location=0) in, naming the same slot. The location numbers must match; the rasterizer automatically interpolates the value across each triangle's surface, so each fragment gets a weighted blend of the three vertex colors rather than a single flat color.

The readFile helper reads the compiled .spv file into a std::vector<char>. Two flags matter: ios::ate positions the cursor at the end so tellg() returns the file size without a separate seek; ios::binary suppresses text-mode transformations — on Windows, opening in text mode converts CR/LF pairs to single LF characters, which would corrupt binary SPIR-V data at any byte pair that happens to match that pattern.

VkShaderModule is created with VkShaderModuleCreateInfo, which requires codeSize in bytes and pCode as a const uint32_t* pointer to the bytecode. The cast from char* to uint32_t* is valid because std::vector's default allocator satisfies worst-case alignment — the data is guaranteed to be at least 4-byte aligned. Creating the module does not compile it to GPU machine code; that happens later, during vkCreateGraphicsPipeline.

VkPipelineShaderStageCreateInfo wires each module into a specific pipeline stage. The stage field identifies where it runs (VK_SHADER_STAGE_VERTEX_BIT or FRAGMENT_BIT). pName names the entry point — explicitly "main" here, but a single SPIR-V binary can contain multiple entry points with different names, allowing one compiled file to serve multiple pipeline configurations. pSpecializationInfo allows compile-time constants to be injected at pipeline creation, further reducing the need for separate shader variants; it is nullptr in this tutorial. Once vkCreateGraphicsPipeline finishes, the SPIR-V has been compiled into GPU machine code and the VkShaderModule objects can be destroyed immediately — they do not belong in the cleanup() function.

Step-by-Step — Shader Module Workflow
  1. Write shader.vert and shader.frag GLSL source files in a shaders/ directory
    WHYVulkan does not accept GLSL at runtime — the source must be compiled offline. Keeping shaders in a subdirectory makes the compile script's paths predictable.
  2. Run glslc shader.vert -o vert.spv and glslc shader.frag -o frag.spv via a build script
    WHYglslc validates GLSL syntax and semantics, then emits SPIR-V bytecode. The -o flag names the output. Must be re-run whenever the shader source changes.
    WATCH OUTThe .spv files must be in the working directory the executable expects at runtime — typically alongside or relative to the binary.
  3. Implement readFile() with std::ios::ate | std::ios::binary
    WHYate positions the read cursor at the end immediately on open, so tellg() gives the file size without a second seek. binary mode is mandatory — text mode on Windows corrupts SPIR-V by mangling CR/LF byte pairs.
  4. Implement createShaderModule(): fill VkShaderModuleCreateInfo with codeSize = code.size() and pCode = reinterpret_cast<const uint32_t*>(code.data()), then call vkCreateShaderModule
    WHYThe module is a staging wrapper — it does not yet compile to machine code. pCode must be uint32_t-aligned; std::vector's allocator guarantees this.
    WATCH OUTcodeSize is in bytes, not in uint32_t elements. Passing the wrong unit would cause the driver to read past the buffer.
  5. In createGraphicsPipeline(), create one VkPipelineShaderStageCreateInfo per programmable stage with stage, module, and pName = "main"
    WHYThis is how the pipeline knows which shader runs at each stage. pName selects the SPIR-V entry point by name — a single module can hold multiple entry points, chosen here at pipeline-creation time.
  6. Destroy both VkShaderModule objects with vkDestroyShaderModule immediately after vkCreateGraphicsPipeline returns — inside createGraphicsPipeline(), not in cleanup()
    WHYPipeline creation converts SPIR-V to GPU machine code. Once that's done the bytecode in the module is no longer referenced — destroying it frees memory and avoids keeping the object alive unnecessarily through the application's lifetime.
Quiz — 8 Questions
Q1
conceptual
Why does Vulkan require SPIR-V bytecode rather than accepting GLSL or HLSL source strings at runtime like OpenGL?
ASPIR-V compiles faster at runtime than GLSL, reducing application startup time
BGPU vendors' GLSL compilers historically interpreted the spec inconsistently, causing cross-vendor incompatibilities; SPIR-V is a single unambiguous format that all vendors receive the same input from
CGLSL is a proprietary format owned by OpenGL; Vulkan needed a format it could license independently
DSPIR-V allows shaders to be encrypted before distribution, protecting intellectual property
Q2
gotcha
Why must readFile() open the .spv file with std::ios::binary? What breaks without it?
AWithout it, the file is read as UTF-16, corrupting single-byte SPIR-V values
BWithout it, std::ifstream refuses to read files larger than 64 KB
CWithout it, text mode is used on Windows, which converts CR/LF byte pairs to single LF characters — corrupting any SPIR-V byte sequence that happens to match 0x0D 0x0A
DWithout it, seekg(0) does not reset to the beginning of the file, causing readFile() to return an empty buffer
Q3
gotcha
VkShaderModuleCreateInfo.pCode is typed as const uint32_t* but the buffer is std::vector<char>. Why is the reinterpret_cast safe here, and what is the underlying requirement?
AThe cast is safe because std::vector's default allocator guarantees worst-case alignment, satisfying the uint32_t (4-byte) alignment required by the Vulkan spec for pCode
BThe cast is safe because char and uint32_t have the same size on all platforms Vulkan targets
CThe cast is safe as long as the vector contains an even number of elements; odd-length bytecode requires padding
DThe cast is unsafe and should be replaced with memcpy into a std::vector<uint32_t> buffer first

terminology
In the vertex shader, what does gl_VertexIndex provide, and what does gl_Position represent?
Agl_VertexIndex is the instance ID for instanced rendering; gl_Position is a 2D screen-space coordinate in pixels
Bgl_VertexIndex is the draw call number; gl_Position is the 3D world-space position before projection
Cgl_VertexIndex is the triangle face index; gl_Position is the final NDC coordinate after perspective division
Dgl_VertexIndex is the index of the vertex being processed (normally indexing a VBO; here used on hardcoded arrays); gl_Position is the vertex's clip-coordinate vec4 output — divided by w to produce NDC during rasterization

conceptual
How does fragColor travel from the vertex shader to the fragment shader, and what does the rasterizer do to it along the way?
AThe vertex shader outputs it with layout(location=0) out; the fragment shader receives it with layout(location=0) in at the matching slot; the rasterizer linearly interpolates the value across all fragments the triangle covers
BfragColor is a global shared-memory variable accessible to both stages simultaneously; no rasterizer involvement
CThe vertex shader writes fragColor to a uniform buffer; the fragment shader reads the same uniform; the rasterizer selects the nearest vertex's value per fragment
DBoth shaders declare fragColor as an inout parameter; it is passed by reference through the pipeline with no interpolation

When exactly are VkShaderModule objects destroyed, and why not in cleanup()?

Q8
gotcha
The triangle's vertex shader hardcodes positions[gl_VertexIndex] instead of reading from a vertex buffer. Why is this approach used here, and what does it tell you about gl_VertexIndex's normal role?
AHardcoded arrays are faster than vertex buffers; this is the recommended approach for small geometry in production
BVertex buffers don't exist yet in Vulkan 1.2; gl_VertexIndex was introduced as a replacement
CVulkan requires at least one draw call before vertex buffers can be bound; hardcoding avoids a chicken-and-egg initialization problem
DVertex buffers haven't been covered yet in the tutorial, so hardcoded arrays avoid that prerequisite; normally gl_VertexIndex is used to fetch data from a bound VBO, making it the bridge between the pipeline and application-provided geometry
