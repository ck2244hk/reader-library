A render pass only describes attachments in the abstract — formats, load/store ops, layouts. A VkFramebuffer is what binds those abstract slots to real VkImageView objects — and because the swap chain hands back a different image each frame, one framebuffer per swap chain image is required.

How the Pieces Bind Together
VkRenderPass — describes attachment 0 as —> format + loadOp/storeOp + layout (abstract)
VkFramebuffer — binds attachment 0 to —> a real VkImageView
A render pass is created once. A framebuffer is created once per swap chain image — three swap chain images means three VkFramebuffer objects, each wrapping a different VkImageView but referencing the same VkRenderPass.

Logic Flow

The render pass chapter defined what an attachment looks like in the abstract: its format, its sample count, what happens to its contents at the start and end of the pass, and what layout it transitions through. None of that description points at any actual memory — VkAttachmentDescription is a template, not a binding. The framebuffer is the object that fills in that template with real image views. vkCmdBeginRenderPass, called later during command buffer recording, takes a VkFramebuffer (not a VkRenderPass) as its rendering target — the framebuffer is what makes the abstract render pass concrete for a specific frame.

Because the swap chain cycles through multiple images for presentation (commonly two or three, decided by the negotiated imageCount), and each image has its own VkImageView, a single framebuffer cannot serve every frame — the framebuffer's pAttachments array is fixed at creation time to a specific set of image views. The tutorial therefore creates a std::vector<VkFramebuffer> sized to swapChainImageViews.size(), with framebuffer i wrapping image view i. All of these framebuffers share the same VkRenderPass handle — only the underlying image view differs — which is consistent with the render pass compatibility rule: many framebuffers, one compatible render pass.

The VkFramebufferCreateInfo fields mirror what's already known from earlier chapters: width and height come directly from swapChainExtent (the same extent computed during swap chain creation), and layers is 1 because these are ordinary 2D images, not image arrays — the same non-stereoscopic assumption baked into the image view's subresourceRange.layerCount back in the image views chapter. attachmentCount and pAttachments must line up positionally with the attachment descriptions in the render pass: index 0 in the framebuffer's attachment array corresponds to attachment 0 in VkRenderPassCreateInfo.pAttachments, which is the same attachment referenced by VkAttachmentReference.attachment and ultimately by the fragment shader's layout(location=0) output.

Step-by-Step — createFramebuffers()
  1. Declare std::vector<VkFramebuffer> swapChainFramebuffers; as a class member
    WHYOne framebuffer is needed per swap chain image — a vector sized to match swapChainImageViews lets the render loop index into it by the current swap chain image index.
  2. Call swapChainFramebuffers.resize(swapChainImageViews.size())
    WHYPre-allocates exactly one slot per swap chain image view before the creation loop runs.
  3. Loop over each swapChainImageViews[i]; build a local VkImageView attachments[] = { swapChainImageViews[i] }
    WHYEach framebuffer must reference the specific image view for that swap chain image — the array position matches the attachment index expected by the render pass.
  4. Fill VkFramebufferCreateInfo: renderPass = renderPass, attachmentCount = 1, pAttachments = attachments, width/height = swapChainExtent.width/height, layers = 1
    WATCH OUTwidth/height must exactly match swapChainExtent — a mismatch with the actual image view dimensions causes validation errors or undefined rendering results.
  5. Call vkCreateFramebuffer(device, &framebufferInfo, nullptr, &swapChainFramebuffers[i]) inside the loop
    NOTEUnlike vkCreateGraphicsPipelines, there is no batch-creation variant — one call per framebuffer, one framebuffer per swap chain image.
  6. Call createFramebuffers() from initVulkan(), after createGraphicsPipeline()
    WHYFramebuffer creation requires a valid renderPass handle (already created) and valid swapChainImageViews — the pipeline itself isn't a hard dependency, but the tutorial places it last in the initialization chain.
  7. Add a loop calling vkDestroyFramebuffer(device, framebuffer, nullptr) in cleanup(), before destroying the render pass
    WHYFramebuffers reference the render pass and image views; they must be destroyed first, before those dependencies are torn down.
Quiz — 6 Questions
Q1
conceptual
What is the relationship between a VkRenderPass and a VkFramebuffer?
AThey are interchangeable — either can be passed to vkCmdBeginRenderPass since both describe the same attachment information
BThe render pass abstractly describes attachments (format, load/store ops, layouts) without pointing to real memory; the framebuffer binds that abstract description to concrete VkImageView objects
CThe framebuffer is created first and the render pass is derived from it automatically by querying its attachment list
DA render pass contains multiple framebuffers internally, one per subpass
Q2
gotcha
Why does the tutorial create a std::vector<VkFramebuffer> with one entry per swap chain image view, instead of a single shared framebuffer?
AVulkan requires at least 2 framebuffers per render pass for double-buffering to function correctly
BEach framebuffer must use a different VkRenderPass, and the tutorial creates one render pass per swap chain image to pair with it
CA framebuffer's pAttachments array is fixed to specific VkImageView handles at creation time; since the swap chain cycles through different images for presentation, each image's distinct view needs its own framebuffer binding
DA single framebuffer can only be bound to one command buffer at a time, so multiple framebuffers allow concurrent recording on multiple threads
Q3
terminology
What does "render pass compatibility" mean for a VkFramebuffer, and is the framebuffer locked to the exact VkRenderPass object used at creation?
AA framebuffer can only ever be used with the exact VkRenderPass handle passed to VkFramebufferCreateInfo.renderPass — no other render pass object will work
BCompatibility means the framebuffer and render pass must have been created on the same VkDevice; any render pass from that device will work
CCompatibility is determined only by width and height matching swapChainExtent; attachment formats are irrelevant
DA framebuffer is compatible with any render pass that has the same number and types of attachments — it is not locked to the exact VkRenderPass handle used at creation, consistent with the compatibility rule introduced for pipelines
Q4
application
In VkFramebufferCreateInfo, what must width and height match, and what happens if they don't?
AThey must match swapChainExtent.width and swapChainExtent.height — the same extent used to create the swap chain and image views. A mismatch with the actual image view dimensions causes validation errors or undefined rendering behavior
BThey must match the GLFW window's current pixel size at the moment vkCreateFramebuffer is called, independent of the swap chain extent
CThey are advisory hints only; Vulkan clamps them internally to the actual image view dimensions regardless of what is specified
DThey must match the viewport dimensions set via VkPipelineViewportStateCreateInfo, not the swap chain extent
Q5
gotcha
Why is layers = 1 in VkFramebufferCreateInfo for this tutorial, and what concept from an earlier chapter does it mirror?
Alayers refers to the number of mipmap levels in the swap chain images; it mirrors the baseMipLevel field from VkImageViewCreateInfo.subresourceRange
Blayers refers to the number of layers in the image arrays the framebuffer is used with; it's 1 because the swap chain images are ordinary single (non-stereoscopic) images — mirroring subresourceRange.layerCount from the image views chapter
Clayers refers to the number of color blend attachments active; it mirrors colorBlendAttachmentCount from the fixed-function pipeline state
Dlayers refers to the number of subpasses in the render pass; it must equal VkRenderPassCreateInfo.subpassCount
Q6
sequence
Why must vkDestroyFramebuffer be called on every framebuffer before vkDestroyRenderPass and before destroying the swap chain image views, during cleanup?
AVulkan automatically destroys framebuffers when their render pass is destroyed, so the order doesn't strictly matter — the tutorial does it for code clarity only
BFramebuffers must be destroyed last, after the device itself, since they are the final consumer of all other Vulkan resources
CA framebuffer holds references to the render pass and the image views it was created with; destroying those dependencies first while the framebuffer still references them would leave dangling handles — dependents must be destroyed before their dependencies
DFramebuffers don't need explicit destruction at all — only vkDestroyImageView and vkDestroyRenderPass need to be called, and the framebuffer cleanup loop is purely defensive boilerplate
