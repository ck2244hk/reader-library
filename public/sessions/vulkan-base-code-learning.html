Complete Base Code
HelloTriangleApplication — full skeleton
#define GLFW_INCLUDE_VULKAN #include <GLFW/glfw3.h> #include <iostream> #include <stdexcept> #include <cstdlib> const uint32_t WIDTH = 800; const uint32_t HEIGHT = 600; class HelloTriangleApplication { public: void run() { initWindow(); initVulkan(); mainLoop(); cleanup(); } private: GLFWwindow* window; void initWindow() { glfwInit(); glfwWindowHint(GLFW_CLIENT_API, GLFW_NO_API); glfwWindowHint(GLFW_RESIZABLE, GLFW_FALSE); window = glfwCreateWindow(WIDTH, HEIGHT, "Vulkan", nullptr, nullptr); } void initVulkan() { // Vulkan object creation will be added here } void mainLoop() { while (!glfwWindowShouldClose(window)) { glfwPollEvents(); } } void cleanup() { glfwDestroyWindow(window); glfwTerminate(); } }; int main() { HelloTriangleApplication app; try { app.run(); } catch (const std::exception& e) { std::cerr << e.what() << std::endl; return EXIT_FAILURE; } return EXIT_SUCCESS; }
Logic Flow

The base code chapter's purpose isn't to do any Vulkan work — it establishes the skeleton that every subsequent chapter fills in. The class-based design is a deliberate choice: by making all Vulkan and GLFW handles private members of HelloTriangleApplication, the tutorial ensures that object lifetimes are tied to the class, creation order is visible in run(), and destruction order can be controlled explicitly in cleanup(). Scattered globals would make both of these properties opaque.

The three-method structure — initWindow(), initVulkan(), mainLoop() — reflects a hard separation of concerns that persists across all chapters. GLFW setup lives only in initWindow(); everything Vulkan lives in initVulkan() (expanded into sub-calls as chapters progress); frame work eventually lives in mainLoop(). This separation makes it easy to locate where new code belongs as the tutorial grows to dozens of Vulkan objects.

Resource management is intentionally manual. C++ RAII patterns (smart pointers, destructors) could manage Vulkan object lifetimes automatically, but the tutorial avoids them to keep each vkCreate/vkDestroy pair explicit and traceable. This is purely pedagogical: in a production Vulkan codebase you would use RAII wrappers such as those provided by vulkan.hpp. The tutorial's manual approach makes visible the API contracts that RAII would otherwise hide.

The two GLFW window hints are load-bearing, not cosmetic. GLFW_NO_API is critical: omitting it causes GLFW to attempt OpenGL context creation, which conflicts with Vulkan's surface setup and produces cryptic errors. GLFW_RESIZABLE being false sidesteps swap chain recreation — a non-trivial topic saved for a dedicated chapter. Both hints signal that the tutorial is actively deferring complexity rather than ignoring it.

Error propagation follows a single pattern throughout the tutorial: Vulkan helper functions throw std::runtime_error on failure, which bubbles up through run() and is caught in main() where e.what() is printed. The VkResult-checking convention is thus hidden inside helpers — but the base code establishes where those throws land and how they terminate the program cleanly.

Step-by-Step — Building the Base
  1. Include GLFW with Vulkan support
    WHYUsing #define GLFW_INCLUDE_VULKAN before the GLFW header makes GLFW pull in vulkan/vulkan.h automatically, ensuring the two headers don't conflict.
    WATCH OUTThe define must come before the GLFW include — defining it after has no effect.
  2. Define HelloTriangleApplication with a run() entry point
    WHYCentralizing all state as private members and exposing only run() keeps the public interface minimal and makes the init → loop → cleanup sequence explicit.
  3. Implement initWindow()
    WHYCreates the OS window that Vulkan will render into. Must run before initVulkan() because surface creation (in a later chapter) requires a valid window handle.
    WATCH OUTSet GLFW_CLIENT_API to GLFW_NO_API — the default opens an OpenGL context that breaks Vulkan surface setup. Set GLFW_RESIZABLE to GLFW_FALSE to avoid swap chain recreation complexity until it's covered.
    • a. glfwInit()
    • b. glfwWindowHint(GLFW_CLIENT_API, GLFW_NO_API)
    • c. glfwWindowHint(GLFW_RESIZABLE, GLFW_FALSE)
    • d. window = glfwCreateWindow(WIDTH, HEIGHT, "Vulkan", nullptr, nullptr)
  4. Add initVulkan() placeholder
    WHYAn empty method now; subsequent chapters add vkCreate calls here in dependency order (instance → device → swap chain → pipeline → ...).
  5. Implement mainLoop()
    WHYKeeps the window alive and responsive by pumping OS events each iteration. The while condition checks for the window-close event set by GLFW when the user closes the window.
    WATCH OUTglfwPollEvents() must be called every iteration — without it the OS marks the window as unresponsive.
  6. Implement cleanup()
    WHYVulkan objects are not reference-counted — every created object must be explicitly destroyed or validation layers will report leaks. Cleanup runs in reverse-creation order.
    WATCH OUTDestroy Vulkan objects before GLFW teardown. Destroying the window before Vulkan objects that reference its surface produces undefined behaviour.
    • a. (future) Destroy all Vulkan objects in reverse order
    • b. glfwDestroyWindow(window)
    • c. glfwTerminate()
  7. Wrap run() in try/catch in main()
    WHYVulkan helper functions will throw std::runtime_error on failure. Catching here ensures errors surface with a readable message instead of a crash.
    WATCH OUTCatching std::exception (not just std::runtime_error) is intentional — the tutorial also notes standard library exceptions like std::bad_alloc can propagate from Vulkan calls.
