The logical device is the first Vulkan object that creates real GPU-side state — it translates queue family indices and feature requirements into a working interface, and its queues are the only channel through which commands reach the GPU.

Logic Flow

Physical device selection was a pure query phase — no GPU-side state was created. Creating the logical device is where that changes. vkCreateDevice allocates the driver's internal representation of this application's connection to the GPU, including the queues. From this point, VkDevice is the handle passed to almost every subsequent Vulkan function.

VkDeviceQueueCreateInfo expresses "give me N queues from queue family index M." The tutorial requests one queue from the graphics family found in the previous chapter. Queue priority is a mandatory field even with a single queue — it governs relative scheduling when multiple queues compete for GPU time. The priority float must stay alive until vkCreateDevice returns, which is why it's a local variable in the same scope.

VkPhysicalDeviceFeatures plays a different role here than in the suitability-check chapter. In the previous chapter it was filled by vkGetPhysicalDeviceFeatures to query what the GPU supports. Here it's zero-initialised to declare what the logical device should enable — all false means no optional features are requested. Later chapters flip specific fields to VK_TRUE when features like anisotropic filtering become needed.

Device-level extensions are separate from instance-level extensions. Instance extensions (like VK_EXT_debug_utils and the GLFW surface extensions) were set on VkInstanceCreateInfo. Device extensions (like VK_KHR_swapchain for presentation) go on VkDeviceCreateInfo. None are needed yet, so enabledExtensionCount = 0. The validation layer fields on VkDeviceCreateInfo are a compatibility holdover — modern Vulkan is single-layer-namespace and implementations ignore them, but older drivers expected them to be populated.

After vkCreateDevice, vkGetDeviceQueue retrieves a handle to the graphics queue. This call doesn't create anything — the queue already exists as a consequence of device creation. The third parameter is the queue index within the family (0 for the first, and the only queue requested). The resulting VkQueue handle is implicitly destroyed with the device, so no explicit cleanup call is needed for it. VkDevice itself, however, must be explicitly destroyed in cleanup() and must be the very first Vulkan call there — before the debug messenger and before vkDestroyInstance — because all objects created from the device depend on it.

Step-by-Step — Creating the Logical Device
  1. Add VkDevice device and VkQueue graphicsQueue as private class members
    WHYBoth must persist for the application's lifetime. VkQueue is implicitly tied to the device — no separate cleanup call is needed for it.
  2. Call createLogicalDevice() from initVulkan() after pickPhysicalDevice()
    WHYLogical device creation depends on a valid VkPhysicalDevice handle; pickPhysicalDevice() must run first to populate it.
  3. Fill VkDeviceQueueCreateInfo with the graphics family index, queueCount = 1, and priority = 1.0f
    WHYSpecifies exactly which queues to create. One graphics queue is sufficient — command buffers from many threads can be recorded in parallel and submitted together through it.
    WATCH OUTpQueuePriorities cannot be null even with a single queue. Keep the float variable in scope until after vkCreateDevice returns.
  4. Zero-initialise VkPhysicalDeviceFeatures deviceFeatures{}
    WHYValue-initialisation sets all feature flags to VK_FALSE. No optional features are needed yet; future chapters set specific fields to VK_TRUE as features are introduced.
  5. Fill VkDeviceCreateInfo, linking queue infos, features, and validation layers
    WHYAggregates all device creation parameters. Setting enabledExtensionCount = 0 is correct for now — VK_KHR_swapchain is added in the presentation chapter.
    WATCH OUTSet the validation layer fields on VkDeviceCreateInfo for compatibility with older implementations, even though modern Vulkan ignores them.
  6. Call vkCreateDevice(physicalDevice, &createInfo, nullptr, &device) and check for VK_SUCCESS
    WHYThe first call that allocates real GPU-side driver resources. From here, device is valid and all subsequent Vulkan object creation passes it as the first argument.
  7. Call vkGetDeviceQueue(device, graphicsFamily, 0, &graphicsQueue)
    WHYRetrieves the handle to the queue that was created as part of vkCreateDevice. The 0 is the queue index within the family — the only queue in a single-queue setup.
  8. Add vkDestroyDevice(device, nullptr) as the first call in cleanup()
    WHYThe device must be destroyed before the instance. Placing it first in cleanup ensures all device-dependent resources (added in future chapters) are destroyed before the device itself.
    WATCH OUTDo not add a vkDestroyQueue call — queues are implicitly destroyed with the device and there is no such function in the API.
