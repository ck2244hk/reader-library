Vulkan has no default framebuffer — the swap chain is the explicit infrastructure for owning, queuing, and presenting rendered images to the screen, requiring careful negotiation of format, timing, resolution, and queue ownership before a single pixel can be displayed.

Logic Flow

OpenGL and Direct3D 11 provided a default framebuffer — an implicit surface the driver managed on your behalf. Vulkan removes this entirely. The application is responsible for creating, managing, and destroying the infrastructure for displaying rendered images. That infrastructure is the swap chain: a ring of images the renderer writes into while the OS displays the previous one, then swaps them. The VK_KHR_swapchain device extension provides this capability, and it must be explicitly enumerated, verified, and enabled during device creation.

Before the swap chain can be created, three categories of information must be queried from the physical device and surface: surface capabilities (image count limits, current size, supported transforms), surface formats (pixel layout and color encoding pairs), and present modes (the timing strategy for handing images to the display). The querySwapChainSupport helper bundles all three into a SwapChainSupportDetails struct. The physical device is also rejected as unsuitable unless it provides at least one format and one present mode — a swap chain that exists but has no usable configuration is worthless.

With the support details in hand, three chooser functions select the best available option from each category. Surface format selection prefers VK_FORMAT_B8G8R8A8_SRGB with VK_COLOR_SPACE_SRGB_NONLINEAR_KHR — 8-bit BGRA with sRGB gamma, which gives perceptually accurate colors consistent with how image textures are encoded. Present mode selection prefers VK_PRESENT_MODE_MAILBOX_KHR — the "triple buffering" mode where the latest rendered frame replaces waiting frames in the queue, giving the lowest latency without tearing. If MAILBOX isn't available, FIFO (guaranteed on all implementations) is the safe fallback. Swap extent, the image resolution in pixels, requires care on high-DPI displays: when currentExtent has its sentinel value (0xFFFFFFFF), GLFW's glfwGetFramebufferSize must be called to get real pixel dimensions, which are then clamped to the supported min/max range.

Image count is set to minImageCount + 1. The minimum count means the driver may have all images occupied internally when a new frame is requested, causing the application to stall. One extra image reduces that likelihood. The count is then capped at maxImageCount if that field is non-zero — zero has a special meaning of "no maximum," so the cap guard must check for it explicitly.

The image sharing mode is the only field that branches on the queue family configuration from the previous chapter. When the graphics and present families share the same index — common on most hardware — EXCLUSIVE mode is correct: one family owns the image and no transfers are needed. When they differ, CONCURRENT mode allows both families to use the image without explicit ownership hand-offs. The tutorial chooses CONCURRENT here for simplicity, noting that EXCLUSIVE with ownership transfers would technically offer better performance.

After vkCreateSwapchainKHR, the VkImage handles are retrieved with vkGetSwapchainImagesKHR using the two-call pattern. The implementation is allowed to create more images than minImageCount, so the actual count must be re-queried. These VkImage handles are stored for the next chapters, where image views and framebuffers are built from them. The swap chain is destroyed in cleanup with vkDestroySwapchainKHR before vkDestroyDevice.

Step-by-Step — Creating the Swap Chain
  1. Add VK_KHR_SWAPCHAIN_EXTENSION_NAME to the required device extensions list and verify support in checkDeviceExtensionSupport()
    WHYSwap chain support is a device extension, not an instance extension. The physical device must be rejected in isDeviceSuitable() if this extension is absent.
  2. Define SwapChainSupportDetails struct with capabilities, formats, and presentModes fields
    WHYAll three categories of support information are needed to fill VkSwapchainCreateInfoKHR. Bundling them in a struct lets querySwapChainSupport return everything in one call.
  3. Implement querySwapChainSupport() using vkGetPhysicalDeviceSurfaceCapabilitiesKHR, vkGetPhysicalDeviceSurfaceFormatsKHR, and vkGetPhysicalDeviceSurfacePresentModesKHR
    WHYEach query uses the two-call pattern (nullptr first to get count, then fill vector). Formats and present modes can return zero entries — check before resizing the vector.
    WATCH OUTisDeviceSuitable() must call this and verify that both formats and presentModes are non-empty — a device that supports the extension but returns no usable formats is still inadequate.
  4. Implement chooseSwapSurfaceFormat(): prefer VK_FORMAT_B8G8R8A8_SRGB + VK_COLOR_SPACE_SRGB_NONLINEAR_KHR, fallback to availableFormats[0]
    WHYsRGB gamma encoding gives perceptually accurate colors and consistency with image textures, which are also typically sRGB. The fallback ensures the app always gets a valid format.
  5. Implement chooseSwapPresentMode(): prefer VK_PRESENT_MODE_MAILBOX_KHR, fallback to VK_PRESENT_MODE_FIFO_KHR
    WHYMAILBOX gives the lowest latency without tearing on desktop. FIFO is the only mode guaranteed to exist on all implementations, making it the mandatory fallback.
  6. Implement chooseSwapExtent(): return currentExtent when its width is not UINT32_MAX; otherwise call glfwGetFramebufferSize() and clamp to [minImageExtent, maxImageExtent]
    WHYWhen currentExtent.width == 0xFFFFFFFF, the surface is telling the application to choose the extent. Screen-coordinate window dimensions may not match pixel dimensions on high-DPI displays, so framebuffer size must be used.
    WATCH OUTNever pass the GLFW window width/height directly as the extent — use glfwGetFramebufferSize, which returns pixels, not screen coordinates.
  7. Set imageCount to minImageCount + 1, then cap it: if (maxImageCount > 0 && imageCount > maxImageCount) imageCount = maxImageCount
    WHYOne extra image reduces driver stalls. The cap guard must check maxImageCount != 0 first, because 0 means unlimited — naively capping to 0 would set imageCount to 0, which is invalid.
  8. Fill VkSwapchainCreateInfoKHR with the chosen format, color space, extent, image count, imageArrayLayers = 1, and imageUsage = VK_IMAGE_USAGE_COLOR_ATTACHMENT_BIT
    WHYimageArrayLayers is 1 for all non-stereoscopic rendering. COLOR_ATTACHMENT_BIT allows the images to be used as render targets; later chapters that do post-processing would also add TRANSFER_DST_BIT.
  9. Set imageSharingMode: EXCLUSIVE when graphicsFamily == presentFamily; CONCURRENT with queueFamilyIndexCount = 2 and pQueueFamilyIndices pointing to both indices when they differ
    WHYEXCLUSIVE requires explicit ownership transfer commands to share an image across families — faster but more complex. CONCURRENT avoids the transfer commands at a small performance cost; chosen here for simplicity.
  10. Set preTransform = capabilities.currentTransform, compositeAlpha = VK_COMPOSITE_ALPHA_OPAQUE_BIT_KHR, clipped = VK_TRUE, oldSwapchain = VK_NULL_HANDLE
    WHYcurrentTransform means no additional rotation/flip. OPAQUE ignores image alpha for OS compositing. clipped = TRUE gives a performance win for obscured pixels. oldSwapchain is only non-null during recreation.
  11. Call vkCreateSwapchainKHR(device, &createInfo, nullptr, &swapChain), then retrieve image handles with the two-call pattern of vkGetSwapchainImagesKHR
    WHYThe implementation may allocate more images than minImageCount — the actual count must be re-queried after creation. The VkImage handles are stored for use in image view and framebuffer creation in subsequent chapters.
    WATCH OUTStore swapChainImageFormat and swapChainExtent as class members — they are referenced throughout all subsequent rendering setup code.
  12. Add vkDestroySwapchainKHR(device, swapChain, nullptr) to cleanup() before vkDestroyDevice
    WHYThe swap chain is a device-level object — it must be destroyed before the device. The VkImage handles retrieved from the swap chain are owned by the swap chain itself and are implicitly freed with it; do not call vkDestroyImage on them.
