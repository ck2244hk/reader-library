A VkImage holds raw pixel data — a VkImageView wraps it with the interpretation metadata the render pipeline needs to know how to read it: dimensionality, format, channel mapping, and which mip/array slices are accessible.

Key Code
createImageViews() — one VkImageView per swap chain image
void createImageViews() { swapChainImageViews.resize(swapChainImages.size()); for (size_t i = 0; i < swapChainImages.size(); i++) { VkImageViewCreateInfo createInfo{}; createInfo.sType = VK_STRUCTURE_TYPE_IMAGE_VIEW_CREATE_INFO; createInfo.image = swapChainImages[i]; createInfo.viewType = VK_IMAGE_VIEW_TYPE_2D; createInfo.format = swapChainImageFormat; // must match swap chain format // Identity swizzle — each channel maps to itself createInfo.components.r = VK_COMPONENT_SWIZZLE_IDENTITY; createInfo.components.g = VK_COMPONENT_SWIZZLE_IDENTITY; createInfo.components.b = VK_COMPONENT_SWIZZLE_IDENTITY; createInfo.components.a = VK_COMPONENT_SWIZZLE_IDENTITY; // Color image, base mip level only, single non-stereoscopic layer createInfo.subresourceRange.aspectMask = VK_IMAGE_ASPECT_COLOR_BIT; createInfo.subresourceRange.baseMipLevel = 0; createInfo.subresourceRange.levelCount = 1; createInfo.subresourceRange.baseArrayLayer = 0; createInfo.subresourceRange.layerCount = 1; if (vkCreateImageView(device, &createInfo, nullptr, &swapChainImageViews[i]) != VK_SUCCESS) throw std::runtime_error("failed to create image views!"); } }
Cleanup — explicit destruction loop
// In cleanup(), before vkDestroySwapchainKHR: for (auto imageView : swapChainImageViews) vkDestroyImageView(device, imageView, nullptr);

Logic Flow

The swap chain chapter retrieved VkImage handles from vkGetSwapchainImagesKHR. These handles represent the raw pixel buffers the swap chain manages. However, Vulkan's render pipeline cannot consume a VkImage directly — it needs a VkImageView layered on top of it. The view tells the pipeline everything about interpretation: the image's dimensionality (2D in this case), the pixel format, how channels are ordered, and which subset of mip levels and array layers is accessible. Without a view, the pipeline has no way to know what it's looking at.

createImageViews() iterates once per swap chain image, filling a VkImageViewCreateInfo for each. The viewType field declares 2D dimensionality. The format is copied from swapChainImageFormat saved during swap chain creation — the view must use the same format the image was stored in, or the pipeline will misread pixel data. The components field configures channel swizzling: all four channels are set to VK_COMPONENT_SWIZZLE_IDENTITY, meaning no remapping occurs (red bytes are read as red, green as green, and so on). Swizzling has real uses — mapping all channels to a single channel for monochrome display, or reordering channels for compatibility — but identity is correct for standard color rendering.

The subresourceRange defines which part of the image the view exposes. For swap chain images this is always the entire single-layer, single-mip-level color image: aspectMask = VK_IMAGE_ASPECT_COLOR_BIT (not depth or stencil), baseMipLevel = 0, levelCount = 1 (no mipmapping on swap chain images), baseArrayLayer = 0, and layerCount = 1. The layerCount = 1 detail is worth understanding: stereoscopic 3D applications create swap chains with two or more array layers and produce two image views per image — one per eye — each pointing to a different baseArrayLayer. This tutorial targets standard single-view rendering.

The ownership model differs between VkImage and VkImageView. The VkImage handles from the swap chain are owned by the swap chain itself — they are created and destroyed implicitly when the swap chain is created and destroyed. The VkImageView objects are explicitly created with vkCreateImageView and must be explicitly destroyed in cleanup with vkDestroyImageView, in a loop, before vkDestroySwapchainKHR is called. The tutorial notes that image views are sufficient for using images as textures in shaders, but rendering into them as framebuffer color attachments requires one more object: a framebuffer.

Step-by-Step — Creating Image Views
  1. Add std::vector<VkImageView> swapChainImageViews as a class member
    WHYOne view is needed per swap chain image; the vector is parallel to swapChainImages and sized to match it in createImageViews().
  2. Implement createImageViews(): resize the vector, then loop over swapChainImages
    WHYResizing first avoids repeated reallocation during the loop; the loop index is used to store each resulting VkImageView in the corresponding slot.
  3. Fill VkImageViewCreateInfo: set image, viewType = VK_IMAGE_VIEW_TYPE_2D, format = swapChainImageFormat, and all four components fields to VK_COMPONENT_SWIZZLE_IDENTITY
    WHYviewType tells the pipeline the image is 2D. format must exactly match what was chosen in createSwapChain(). Identity swizzle means no channel remapping — standard for color rendering.
    WATCH OUTThe components fields must be explicitly set — do not assume zero-initialization equals IDENTITY. Zero (0) is VK_COMPONENT_SWIZZLE_IDENTITY in practice, but relying on it is fragile; explicit assignment is clearer.
  4. Set subresourceRange: aspectMask = VK_IMAGE_ASPECT_COLOR_BIT, baseMipLevel = 0, levelCount = 1, baseArrayLayer = 0, layerCount = 1
    WHYThese values expose exactly the full single-layer, single-mip-level color image that a standard swap chain image provides. Depth images would use DEPTH_BIT; stereoscopic images would use layerCount = 2.
  5. Call vkCreateImageView(device, &createInfo, nullptr, &swapChainImageViews[i]) and check the return value
    WHYUnlike VkImage handles (implicitly created by the swap chain), VkImageView objects require explicit creation and a successful return check before use.
  6. Call createImageViews() from initVulkan() immediately after createSwapChain()
    WHYThe image views depend on swapChainImages and swapChainImageFormat, which are populated by createSwapChain() — they must exist before any view creation attempt.
  7. In cleanup(), loop over swapChainImageViews and call vkDestroyImageView(device, imageView, nullptr) for each, before vkDestroySwapchainKHR
    WHYVkImageView objects are explicitly owned by the application and must be explicitly destroyed. Destroying them before the swap chain ensures the underlying VkImages they reference are still valid at destruction time.

Q1
terminology
What is the relationship between VkImage and VkImageView, and why can't VkImage be used directly in the render pipeline?
AVkImage and VkImageView are interchangeable — VkImageView is just a convenience alias for the same underlying object
BVkImage contains both pixels and metadata; VkImageView strips the metadata for use in compute shaders
CVkImage is raw pixel storage; VkImageView wraps it with interpretation metadata (dimensionality, format, channel mapping, accessible subresource range) that the pipeline requires
DVkImage is a CPU-side handle; VkImageView is the GPU-resident copy that the pipeline accesses
Q2
terminology
What does the components field of VkImageViewCreateInfo control, and what does VK_COMPONENT_SWIZZLE_IDENTITY mean?
AIt controls which memory heap the image is allocated from; IDENTITY means the default heap is used
BIt remaps color channels before the pipeline reads them (swizzle); IDENTITY means each channel maps to itself — R reads R, G reads G, B reads B, A reads A
CIt sets the pixel format for each channel individually; IDENTITY means the format from the VkImage is inherited unchanged
DIt controls the blend operation between the image and the framebuffer; IDENTITY means additive blending
Q3
application
Why is subresourceRange.layerCount set to 1 for swap chain image views, and when would it be set to a higher value?
ASwap chain images are single-layer (non-stereoscopic); layerCount = 1 restricts the view to that one layer. Stereoscopic 3D applications use layerCount = 2 (or create separate views per eye with baseArrayLayer = 0 and 1)
BlayerCount must always be 1; higher values are used only for cube maps and are set via a separate field
ClayerCount = 1 is a performance optimization; setting it higher enables mipmapped rendering
DlayerCount corresponds to the number of color channels; BGRA images always use layerCount = 4
Q4
conceptual
How does cleanup differ between swapChainImages (the VkImage handles) and swapChainImageViews?
ABoth must be explicitly destroyed — vkDestroyImage for images and vkDestroyImageView for views, in that order
BOnly the images require explicit destruction; image views are freed automatically when the device is destroyed
COnly the image views require explicit destruction; images are reference-counted and freed when no views reference them
DVkImage handles are owned by the swap chain and freed implicitly by vkDestroySwapchainKHR; VkImageView objects are explicitly created by the application and must be explicitly destroyed with vkDestroyImageView
Q5
gotcha
subresourceRange.aspectMask is set to VK_IMAGE_ASPECT_COLOR_BIT for swap chain image views. What would it be set to for a depth buffer image view?
AVK_IMAGE_ASPECT_COLOR_BIT — aspectMask is always COLOR_BIT regardless of image content
BVK_IMAGE_ASPECT_NONE — depth images have no aspect and are accessed directly
CVK_IMAGE_ASPECT_DEPTH_BIT — the aspect declares what the image stores; depth images use DEPTH_BIT so the pipeline knows to interpret the data as depth values
DVK_IMAGE_ASPECT_COLOR_BIT | VK_IMAGE_ASPECT_DEPTH_BIT — all image views must include COLOR_BIT as a base flag
